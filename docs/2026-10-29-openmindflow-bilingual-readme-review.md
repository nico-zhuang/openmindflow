## 专家观点（第一人称模拟）

- **产品聚焦／乔布斯框架**：我先让读者看懂“独立 macOS 思维导图编辑器”，再看到一项最有辨识度的体验——自己的 `.mflw` 文稿与不回写原 `.mindnode`。论据是现有首屏被发行日志和哈希淹没；前提是读者先判断是否适用再考虑安装。我不同意把全部版本史铺在首页。盲区是只展示图标不一定能解释真实编辑体验。
- **信息效率／张一鸣框架**：我把路径缩成“这是什么 → 能做什么 → 怎样取得 → 兼容到哪”。中文与英文分别成页、保持相同顺序和相互导航，比每段中英交错更容易阅读。前提是两页事实同步维护；我不同意过多首屏宣传语。盲区是两个 README 随版本演进可能失同步。
- **诚实写作／Paul Graham 框架**：我会先写具体动作与明确限制，而不把“Stable”写成 Apple 的安全背书；缺 LICENSE 就不称开源，私有仓库不写公共下载承诺。前提是现有 Release 证据可核对；我反对把限制藏在文末。盲区是限制过度前置可能压住产品介绍。
- **读者留存／MrBeast 框架**：我希望首屏有一张立刻可辨认的真实图和明确下载入口，但不能把旧离屏画布渲染当成完整 App 截图。前提是图像真实且与现版一致；我和保守派分歧在展示的优先级。盲区是纯文本页面对首次到访者不够直观。
- **可传播结构／X 导师框架**：我会让标题、一句话定位和几个能力标题可独立引用，英文不是逐字机器翻译，而是同事实、同边界的自然表述。前提是双语不引入新的功能承诺；我不同意编造社区反馈或增长数字。盲区是长期更新需要双语同步检查。

## 模式结果与综合

**条件共识**：采用“中文默认 README＋独立英文 README、双向语言入口、统一信息架构”；首屏使用已确认的产品图标和真实静态徽章，下载入口紧邻 PRIVATE／ad-hoc／手动升级提示。仅在有可核对的当前版本真实窗口截图时才把它当产品截图；旧离屏画布不放首屏。历史开发长日志原样存档且从首页可达。分歧保留：图像能提高理解效率，但展示未经实体 GUI 验收的截图会制造错误证据。

## 条件化行动及采纳记录

- 若目标是 GitHub 仓库首页而非另建网站：只用 GitHub 支持的 Markdown／安全 HTML，中文 `README.md` 与英文 `README.en.md` 互相导航，不引入运行时或脚本切语；产品图标是仓库本地图片，少量静态状态徽章由 shields.io 提供，不以外链截图承载产品事实。**采纳**。
- 若后续取得实际 v0.6.1 原生窗口且用户允许展示：可增补当前包的真实截图并标注来源；目前不把历史离屏画布冒充实机。**本轮不采用截图**。
- 若首屏被权限与下载占满：在限制提示前加一行可核对的编辑／保存能力，并让文稿格式单独成节；中英结构同步。**独立页面审查后已实际修改两页**。
- 若仍需调查旧版细节：保留仓库根目录的 `README.history.md` 逐字节归档，首页只给历史入口；归档继续使用原先相对仓库根的链接。**采纳，且按独立审查意见修正了归档位置**。
- 参考页面的动态 Star 数、MIT 徽章、“完全开源”“任意 MindNode 文件无损兼容”以及未经验证的用户评价，均与本项目证据不符。**不采纳**。
