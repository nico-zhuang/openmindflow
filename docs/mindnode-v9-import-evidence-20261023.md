# MindNode v9 导入信息证据清单（2026-10-23）

## 范围与结论边界

本记录只核查用户明确授权的 **一份** 原版 `.mindnode` 私有副本（4 张导图、65 个节点），以及本机已安装的 MindNode 主题资源。只读取自有 `0700` 副本，没有修改原件、副本、正在运行的窗口或旧预览；报告不收录私人正文、节点 UUID、主题 UUID、原始 plist 或附件。此前曾在原版 App 中查看此副本的窗口，但下表的字段结论来自静态文件，不等于已经通过受控编辑验证了运行时语义。

**目前只是树结构加局部线条样式导入，不是完整打开。** 现有 [导入器](../Sources/MindNodeImporter.swift) 提取 UUID、纯文本、子节点、折叠状态和每节点路径颜色／线宽；[模型](../Sources/MapModel.swift) 不表示源坐标、原生标题宽度/字体、主题或跨节点连线；[布局](../Sources/Layout.swift) 重算全部 x/y 与文字尺寸。其余字段虽仍存在于获授权的源副本中，却没有进入当前 GUI 模型；保存为自有 JSON 时也不会带上。

## 已观察到的字段及当前损失

| 范围 | 已观察到的 v9 数据（仅此样本） | 当前处理与影响 | 尚不能断言 |
| --- | --- | --- | --- |
| 容器 | 二进制 plist `contents.xml`；`version=9`，另有 `typeOptions` 与打印设置；4 个 `canvas.mindMaps` | 导入器校验版本并取各 `mainNode`，其余文档设置丢失 | 其他版本、ZIP 容器及未知字段语义 |
| 坐标 | 65/65 节点有 `location`，编码为 `{x, y}` 小数字符串；4 个根的坐标不在一条统一列，子节点水平位移也不恒定 | 导入器丢弃位置，`mapLayout` 按深度固定列宽、树高与 32pt 间距重新排版；所以原版节点位置无法重现 | 位置代表中心、左上角或标题锚点？文档坐标如何映射视口？是否随自动布局而改写？ |
| 宽度 | 65/65 标题有 `maxWidth` 浮点值及 `allowToShrinkWidth` 布尔值；63 个是 `(300,true)`，两处第四层节点是 `(316,false)`、`(136,false)` | 两字段均丢弃；GUI 自有宽度是 Auto 或 170/240/320/480pt 右键预设，文字布局使用 `min(320,max(170,内容宽+24))` | 两个异常值与手动拖宽相关只是**相关性**，不是因果证据；最小值、单位和自动收缩/折行规则待验证 |
| 富文本和字体 | 64 个标题是 `<p style="…">`，1 个标题为空；4 个根段落写 `font:36px`、居中，非空后代写 `font:24px`、左对齐；段落 CSS 包含 `Songti SC` / `STSongti-SC-Regular`、颜色等 | `plainTitle` 只取文字，丢弃整个段落属性；画布/布局改用固定 20pt/16pt 宋体，无法还原字号和每节点属性 | CSS 与主题字体、显式 `fontStyle` 哪个最终生效，以及跨平台回退行为 |
| 节点字体覆写 | 仅 1/65 节点有 `title.fontStyle`（`STSongti-SC-Regular`、24pt，含颜色/对齐/加粗等字段）；其余 64 个没有此键，所有节点 `styleChangedByUser=false` | 显式覆写也丢失；不能把“没有 fontStyle”解释成“没有字号信息” | `styleChangedByUser` 与字体覆写并非简单等价；继承优先级须受控比对 |
| 节点外观 | 65/65 有 `shapeStyle`（`shapeType`、`fillColor`、`borderStrokeStyle`）和 `pathStyle.strokeStyle`（色/宽/虚线）；根形状值与子节点不同 | 只保留路径 RGBA/宽度显示；根形状、填充、边框和虚线未读取用于显示 | 数值枚举与每种实际轮廓、系统浅深色变化 |
| 导图布局 | 4/4 `mindMaps` 有 `branchType`、`branchWidthType`、`layoutStyle`、`layoutOptions.layoutSpacing`、`styleAdjustmentType`；本样本各图取值相同 | 全部丢弃；只能说明字段存在，不能靠单一样本解码枚举 | 换布局/主题后各枚举的具体行为与优先级 |
| 画布与视图 | `canvas.color` 是四通道 RGBA 字符串，与包内主题 `backgroundColor` 完全相同；另有 `viewState.plist` 的缩放、滚动中心及窗口状态 | 当前画布用自身背景/外观，不使用原画布色；既不恢复源视口也不导入视图状态 | 文档主题背景与系统黑灰背景的适配规则；视图状态是否应作为个人窗口偏好独立处理 |
| 跨节点连接 | `canvas.crossConnections` 有 2 条：节点 ID 两端点、箭头、标题、线型与含 `wayPointOffset` 的路径布局 | 均未进入模型，原版虚线/非树形关系在本应用消失 | waypoint 相对哪个坐标、连线锚点的计算方式 |
| 附件与杂项 | 包内另有 1 张 JPG；65/65 节点有 `attachmentPosition` 与 `styleChangedByUser` | 附件和展示位置未导入，也不随自有 JSON 保存 | JPG 与哪个节点关联、附件显示方式；不能仅凭扩展名推断图片意义 |

RGBA 字符串格式在本样本为四个 0–1 数值 `{r, g, b, a}`；上述统计仅证明字段可读，不把未知颜色空间/主题渲染行为当成已经还原。

## 主题模板并非“只有原参数”

包内存在**嵌入式** `style.mindnodestyle/metadata.plist`（`id/title/author/version`）及 `style.mindnodestyle/contents.xml`（`backgroundColor`、根/基础子节点样式、6 个分支颜色、跨连线模板等）。嵌入元数据的 ID/标题/作者与已安装的 **Swing** 传统主题元数据相符，但嵌入版与已安装主题的版本及一个根节点形状值不同；已安装的同名**动态**主题使用不同 ID 和另一套字体/浅深色 JSON 结构。不能用“同名”替代“同 ID”，更不能从主题安装包覆盖文档嵌入值。

嵌入的传统主题给根/基础子节点记录 `TimesNewRomanPSMT` 的 36/24 字体设置；同一实际文档的标题段落 CSS 记录 `STSongti-SC-Regular` 的 36/24px。二者不一致，说明**必须区分文档内最终富文本、主题默认值及每节点覆写**；只观察字段不能确定原版运行时的最终优先级。也没有证据证明顶层另有独立 `canvas.themeID`：本样本的主题身份位于嵌入主题元数据中。

## 下一步的可证伪调查（仍不修改用户原件）

1. **先构建只读字段映射与无损证据**：对这 65 个 UUID 建立内部坐标、标题 CSS、宽度/收缩标志、节点造型、主题资源与跨节点连接的覆盖检查；保留未解释字段原值，不能再把纯文本树假称完整导入。
2. **分离坐标与宽度实验**：在新的 `0700` 自有临时副本中，原版 MindNode 每次只调整**一个**节点的宽度或位置并另存；比较同一 UUID 的 `location`、`maxWidth`、收缩标志、父子位置和视图状态，验证单位/锚点/自动布局变化。没有受控前后样本就不称现已支持自由拖宽。
3. **分离字体与主题实验**：分别只改一处根/子节点字号及一次主题，比较标题 CSS、显式 `fontStyle`、嵌入 `style.mindnodestyle` 的 ID/内容及节点覆写；用原版 App 实际重新打开隔离样本确认优先级。文件中的“36/24”不能直接等同屏幕上的点数。
4. **按证据实现导入**：先忠实展示源坐标、真实宽度和字体（保留已有系统外观切换/用户认可的分支颜色）；再处理主题资源、跨节点关系和附件。每项用合成 v9 安全测试、授权副本只读覆盖检查及独立原生窗口验证；不要覆盖当前运行的预览或原始文件。
5. **最后才做 `.mindnode` 另存**：新增/删除、主题切换、手动宽度及资源都能从原版文件中受控验证后，才把同格式保存接入 GUI；未到此处时 Save 仍仅另存自有 JSON，并明确告诉用户。

**证据边界：** 本清单只覆盖一份经授权的 v9 包与本机已安装的 Swing 资源，不声称适用于任意 MindNode 主题或版本。字体优先级、布局枚举、主题切换持久化、宽度拖拽语义及原版再次打开尚需隔离前/后样本；这些未知项不应被静态字段计数掩盖。
